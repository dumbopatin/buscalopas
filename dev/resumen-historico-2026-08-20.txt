ARQUITECTURA DE DATOS / DOBLE BACKEND
--------------------------------------------------------------------------------
- Si SUPABASE_URL + anon key están en config.js → el cliente usa Supabase (tabla scores: name, score, total, pass, stats).
- Si no hay Supabase o falla → fetch a server.js (scores.json) / localStorage.
- API de server.js: /api/leaderboard (AHORA devuelve TODOS los jugadores ordenados, no top 10), /api/players,
  /api/player, /api/score (POST), /api/notes (GET/POST), /api/friends (GET {friends,incoming,outgoing} /
  POST request|accept|decline|cancel|remove), /api/user?name= (existe o no), /api/search?q=, /api/chat (GET/POST).
  server.js SOLO se usa en local/dev/tests. En Netlify (producción) los amigos/chat/notas van a Supabase.
- CAPA SUPABASE DE AMIGOS/CHAT/NOTAS (19/08, 3ª sesión): si supabaseClient está activo, game.js usa:
  - friends: loadFriends() = friendships (user_a<user_b) + friend_requests (from/to). postFriendAction():
    request→insert friend_requests (upsert onConflict), accept→delete request + upsert friendships,
    decline/cancel→delete request, remove→delete friendships por par ordenado. userExists()/searchUsers()
    ya consultaban la tabla scores de Supabase (siguen igual).
  - chat: loadChat() = 2 selects (name→with y with→name) por created_at asc, se fusionan con el espejo
    localStorage; sendChatMessage() inserta en chat_messages con created_at=Date.now().
  - notas: loadNotes()/saveNotes() usan la tabla notes POR USUARIO (username PK, upsert onConflict).
    OJO: en el server.js local las notas eran globales; en Supabase ahora son por usuario.
  - openPlayerModal() ahora usa fetchPlayerData() (Supabase-aware) en vez de /api/player directo, así el
    perfil del ranking muestra datos en Netlify. Si data.stats es string (columna text), lo parsea.
  - Si Supabase falla (sin red/error), cada función cae a su fallback: localStorage (amigos/chat/notas).
- La cartera y el total se guardan en localStorage ('buscalopas_wallet', 'buscalopas_total') y se sincronizan al servidor.
- statsData (estadísticas por jugador) vive en statsData y se persiste vía saveStats() → localStorage + pushStats().
  Estructura: { games, wins, losses, bestEarning, spizSaved, timePlayed, luciferReached, turulosWins, correctTurulos,
               lopa: { shopUnlocked, owned{}, active{}, charges{milagro,ultimobaile}, levels{spiz,dinero},
                       uses{subidon}, order[] }, by{} }
  - uses.subidon: contador persistente de veces que se ha activado el Subidón.
  - order[]: orden de adquisición de amuletos (para mostrarlos de izquierda a derecha en el HUD).
- by{} guarda partidas por clave "dificultad_tamaño" (ej "0.08-180_10") → {g,w,l}.

--------------------------------------------------------------------------------
MECÁNICA DEL JUEGO
--------------------------------------------------------------------------------
- Tablero tamaño 10/15/20 (desbloqueables en tienda). Dificultad = ratio de minas-tiempo:
  "0.08-180" Fácil, "0.12-120" Media (1 victoria), "0.16-60" Difícil (tienda).
- 3 modos: classic (destapar todo), turulos (marcar todas las minas), hybrid (cualquiera).
- Elementos: minas "papela", celda "spiz" que da tiempo (+20% normal, +40% en Lucifer, +50€ si se guarda al final), turulos = banderas.
- Modo LUCIFER: entra cuando queda ≤20% del tiempo → música, mensajes, pantalla que tiembla.
- Dinero al ganar: timeRemaining × multiplicador (x1 fácil / x5 media / x20 difícil) × 0.1, +bonus de mejoras.
- DINERO POR TURULOS: al final de partida, +1€/turulo correcto en fácil, +2€ media, +3€ difícil. Se cobra también al perder.
  OJO (bug arreglado 19/08): las ganancias usan gameCorrectTurulos (contador de LA PARTIDA), no el
  statsData.correctTurulos (de por vida). gameCorrectTurulos se reinicia en initGame, sube/baja al
  colocar/quitar bandera en mina. statsData.correctTurulos sigue siendo el total de por vida (desbloqueos/progreso).

SESIÓN 19/08 (9ª): "NO CARGA NUNCA DESDE EL MÓVIL" — ARRANQUE OFFLINE
--------------------------------------------------------------------------------
SÍNTOMA: desde el móvil (misma Wi-Fi, vía jugar.sh → http://IP-LAN:3000) la
página se quedaba "cargando para siempre".
CAUSAS (dos):
1) index.html dependía de recursos EXTERNOS que bloquean:
   - <script src="https://cdn.jsdelivr.net/.../@supabase/supabase-js@2"> es
     parser-blocking: si no se descarga, config.js/textos.js/game.js NUNCA se
     ejecutan y la pantalla queda en blanco. Ese era el "no termina de cargar".
   - La fuente de Google (CSS render-blocking) retrasaba el pintado.
2) Al servir supabase en local, supabaseClient SIEMPRE existía y cada query a
   supabase.co reintentaba (postgrest-js: hasta 3 reintentos con backoff ≈7s, y
   más en redes malas) antes de caer al servidor local. El HUD (LopAmuletos)
   esperaba a loadPlayerFromServer para pintarse.
SOLUCIONES:
- Descargado @supabase/supabase-js@2 (212KB, UMD) a vendor/supabase.min.js y
  index.html ahora carga <script src="vendor/supabase.min.js">: CERO dependencia
  de CDN.
- Fuente de Google no bloqueante: <link ... media="print" onload="this.media='all'">
  (si no hay internet, el juego pinta con fuentes de respaldo).
- Sondeo de supabase al arrancar: initSupabase() hace un HEAD a SUPABASE_URL con
  AbortController (timeout 2s, sin reintentos). Solo si responde se crea
  supabaseClient; si no, queda null y TODO usa el servidor local al instante.
  El arranque pinta el menú/HUD desde localStorage y después, si hay supabase,
  carga amigos/ranking/servidor (sin bloquear el pintado).
- supabaseFetch envuelve el fetch del cliente con timeout de 4s por si supabase
  cae a mitad de sesión (devuelve Response 503 → error controlado, cae a local).
- dev/server.js: server.listen(PORT, '0.0.0.0') explícito.
- jugar.sh: detecta la IP de la interfaz de red real (eth/wlan), no la de
  docker/VPN, para imprimir la URL del móvil.
VERIFICADO: 42 tests OK + simulación móvil sin internet (supabase+fuentes+CDN
abortados): LopAmuletos visibles en 157ms. En test, el HUD pinta al instante
(antes tardaba 5-7s esperando los reintentos de supabase).
